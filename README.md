# Time Tracker

Локальное Windows-приложение для контроля рабочих интервалов за компьютером. MVP реализует простой цикл: 25 минут работы, затем предложение сделать перерыв. Интерфейс намеренно минимальный и не требует регистрации или подключения к серверу.

## Цель MVP

Помочь пользователю не забывать о коротких перерывах во время работы, не превращая приложение в полноценную систему учёта задач.

### Сценарий работы

1. Пользователь запускает приложение и нажимает «Начать работу».
2. Запускается рабочий таймер на 25 минут.
3. По окончании интервала сверху экрана показывается красная полоска с предложением отдохнуть.
4. Кнопка «Пропустить» сразу запускает новый рабочий интервал на 25 минут.
5. Кнопка «Отдыхать» запускает перерыв на 5 минут.
6. После завершения перерыва автоматически начинается новый рабочий интервал.
7. После пяти завершённых рабочих интервалов вместо короткого перерыва запускается большой перерыв на 90 минут.

### Полоса уведомления

В MVP уведомление реализуется отдельным окном-полосой в верхней части экрана:

- ширина — вся рабочая ширина основного монитора;
- высота — временно 64 px, точное значение уточняется после UX-проверки;
- рабочее состояние — нейтральный цвет/индикатор прогресса;
- время работы закончилось — хорошо заметный красный цвет;
- короткий или большой перерыв — зелёный цвет;
- полоса размещается только на primary monitor;
- при подключении двух и более мониторов второй монитор не перекрывается.

Под «первым монитором» понимается основной монитор Windows, а не физически первый найденный в списке устройств. Окно позиционируется по рабочей области primary display, чтобы не перекрывать системную панель задач.

Счётчик пяти рабочих интервалов сбрасывается после запуска большого перерыва. Нажатие «Пропустить» не считается отдыхом и не сбрасывает счётчик.

## Стек

- **C# / .NET 10 LTS** — основной язык и runtime.
- **WinUI 3 + Windows App SDK** — нативный современный UI Windows на XAML.
- **MVVM Toolkit** — команды, observable-состояние и минимум ручного boilerplate.
- **Generic Host / Microsoft.Extensions.DependencyInjection** — композиция зависимостей и жизненный цикл сервисов.
- **SQLite** — локальное хранение настроек и истории; подключается на этапе, когда появится история сессий.
- **xUnit** — модульные тесты доменной логики.
- **.NET Community Toolkit** — только необходимые пакеты, без тяжёлого фреймворка.
- **WinUI resource files (`.resw`)** — локализация интерфейса на русский и английский языки.

Разработка ведётся по **Test-Driven Development (TDD)**: `Red → Green → Refactor`. Новое поведение сначала описывается падающим тестом, затем реализуется минимально необходимым кодом и после этого улучшается без изменения поведения.

Почему WinUI 3: это официальный нативный UI-стек Microsoft для desktop-приложений Windows, поддерживающий C# и XAML. Он лучше соответствует задаче системного приложения с overlay-уведомлением, чем web-wrapper или кроссплатформенный UI. Для первой версии целевая ОС — Windows 10 1809+ и Windows 11; минимальную версию следует уточнить при создании проекта по актуальной версии Windows App SDK.

### Портативность

Приложение распространяется как ZIP-архив, который можно распаковать в любую папку и запустить без установки, прав администратора, MSIX и записи в системный реестр.

- WinUI 3 используется в режиме **unpackaged**.
- Публикация — **self-contained**, чтобы на компьютере пользователя не требовалась установленная среда .NET.
- В первую очередь поддерживается `win-x64`; `win-arm64` можно добавить отдельным артефактом.
- Настройки, SQLite-база и логи хранятся в подкаталоге `data/` рядом с исполняемым файлом. Это сохраняет переносимость всей папки приложения.
- Приложение не должно писать рабочие данные в `%AppData%` или `%ProgramData%`, если пользователь явно не выбрал такой режим.
- Автообновление, Windows Service и обязательный установщик не входят в MVP.

### Скрытие overlay при демонстрации экрана

`BreakOverlay` будет отдельным top-level окном. При его создании приложение применяет Win32 API `SetWindowDisplayAffinity` со значением `WDA_EXCLUDEFROMCAPTURE`. Это позволяет не включать окно в поддерживаемые Windows-механизмы захвата экрана, которыми обычно пользуются приложения для демонстрации рабочего стола.

Функция доступна начиная с Windows 10 version 2004. Это не DRM и не абсолютная гарантия: она не защищает от съёмки камерой, некоторых нестандартных способов захвата, удалённого доступа и ситуаций, когда приложение для видеозвонка использует собственный pipeline. Поэтому в настройках и документации функция должна называться «Скрывать уведомление при демонстрации экрана», а не обещать стопроцентную невидимость.

В тестовый план входят Microsoft Teams, Zoom и Discord в режимах демонстрации всего экрана и отдельного окна. Если API не применился, приложение продолжает работать, но пишет диагностическое предупреждение в лог.

Ограничение portable-режима: папка приложения должна быть доступна для записи. Если приложение запущено из `C:\Program Files`, `data/` может быть недоступен; рекомендуются Desktop, Documents или отдельная пользовательская папка.

### Локализация

Приложение сразу поддерживает русский (`ru-RU`) и английский (`en-US`) языки.

- пользовательские строки хранятся в `.resw`-ресурсах, а не в XAML, ViewModel или Domain-коде;
- для XAML используется стандартная схема WinUI `x:Uid` и resource keys;
- для строк из Application используется отдельный `IResourceService`, чтобы Application не зависел от WinUI;
- язык по умолчанию определяется из языка Windows, при отсутствии перевода используется английский;
- выбор пользователя сохраняется в `data/settings.json`;
- даты, числа и текстовые шаблоны форматируются через текущую `CultureInfo`;
- локализуются также tooltips, accessibility names, ошибки и системные уведомления.

На первом этапе смена языка может применяться после перезапуска приложения. Динамическая смена без перезапуска — отдельное улучшение после UX-проверки.

## Архитектура

Используется гексагональная архитектура (Ports & Adapters) в форме модульного монолита. Для MVP это даёт строгие границы и тестируемость без преждевременного усложнения в виде микросервисов.

```text
                 ┌─────────────────────────────┐
                 │      Presentation             │
                 │ WinUI/XAML, Views, ViewModels │
                 └──────────────┬──────────────┘
                                │ inbound adapter
                 ┌──────────────▼──────────────┐
                 │       Application            │
                 │ use cases, coordinator, ports│
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │          Domain              │
                 │ entities, value objects,     │
                 │ rules, domain events         │
                 └──────────────┬──────────────┘
                                │ outbound ports
                 ┌──────────────▼──────────────┐
                 │       Infrastructure         │
                 │ Windows API, clock, SQLite,  │
                 │ notifications, file system   │
                 └─────────────────────────────┘
```

Зависимости направлены только внутрь: `Presentation → Application → Domain`, а `Infrastructure` реализует интерфейсы (`ports`), объявленные во внутренних слоях. Domain не знает ни о WinUI, ни о Windows API, ни о SQLite.

### Domain

Домен не должен знать о WinUI, DispatcherTimer, SQLite и Windows API.

- `TimerPhase`: `Idle`, `Work`, `ShortBreak`, `LongBreak`, `AwaitingBreakDecision`.
- `TimerSession`: текущая фаза, оставшееся время, номер завершённого рабочего интервала.
- `TimerRules`: длительности и правило большого перерыва.
- `TimerState`/события переходов — единый источник истины для UI.

Все переходы должны быть описаны как команды/методы доменного уровня. Нельзя определять бизнес-правила в code-behind XAML.

### Application и порты

`TimerCoordinator` управляет сценарием и вызывает порты:

- `IClock` — монотонное измерение времени и тестируемость без реального ожидания;
- `ITimerEngine` — тик/планирование обновлений;
- `INotificationService` — overlay и системное уведомление;
- `ISettingsStore` — настройки пользователя;
- `ISessionRepository` — будущая история интервалов.

Application слой переводит доменные события в состояние, которое наблюдает ViewModel. Реальное время не должно вычисляться сложением количества тиков: оставшееся время считается от `StartedAt`/`Deadline` с использованием устойчивых часов.

### Adapters и Presentation

Основные UI-компоненты:

- `MainWindow` — компактное окно управления текущим таймером;
- `BreakOverlay` — верхняя полоса на primary monitor, меняющая цвет по состоянию таймера;
- `TimerViewModel` — форматирование времени, команды Start/Pause/Skip/Break;
- `SettingsViewModel` — только когда настройки войдут в MVP+.

UI получает состояние через binding. ViewModel не должна напрямую создавать окна и не должна содержать расчёт правила «каждые пять интервалов».

### Правила структуры кода

- Один публичный тип — один файл; имя файла совпадает с именем типа.
- Каждая View, ViewModel, команда, доменная сущность, value object, порт и адаптер находятся в отдельном файле.
- Code-behind содержит только UI-specific код: инициализацию компонента, обработку особенностей WinUI и получение `WindowId`. Бизнес-логика туда не помещается.
- `BreakOverlay` состоит минимум из отдельных `BreakOverlay.xaml`, `BreakOverlay.xaml.cs` и `BreakOverlayViewModel.cs`; применение `SetWindowDisplayAffinity` вынесено в Windows-адаптер.
- Не создавать классы `Utils`, `Helpers` и `Manager` без конкретной ответственности. Предпочитать имя по роли: `SystemClock`, `PrimaryMonitorPlacementService`, `SessionRepository`.
- Интерфейсы портов принадлежат слою, который ими владеет, а не Infrastructure. Например, `IClock` находится в Application, `SystemClock` — в Infrastructure.
- Композиция зависимостей выполняется в одном месте — `TimeTracker.App/Composition/ServiceRegistration.cs`.
- Конструкторы принимают зависимости явно; статические глобальные сервисы и service locator запрещены.
- Внешние типы Windows/SQLite не протекают в Domain и Application-контракты; на границе выполняется преобразование в свои модели.

## Состояния и переходы

```text
Idle --Start--> Work(25m)
Work completed --workCount < 5--> AwaitingBreakDecision
Work completed --workCount == 5--> LongBreak(90m)
AwaitingBreakDecision --Skip--> Work(25m)
AwaitingBreakDecision --Rest--> ShortBreak(5m)
ShortBreak completed --> Work(25m)
LongBreak completed --> Work(25m), workCount = 0
```

В MVP таймер должен корректно переживать сворачивание и потерю фокуса окна. При перезапуске приложения восстановление активной сессии можно отложить; до появления persistence приложение явно показывает состояние «не запущено».

## Предлагаемая структура solution

```text
TimeTracker.sln
src/
  TimeTracker.App/              # WinUI 3, Views, ViewModels, composition root
  TimeTracker.Application/      # use cases, coordinator, inbound/outbound ports
  TimeTracker.Domain/           # чистые модели, value objects и правила
  TimeTracker.Infrastructure/  # адаптеры Windows, clock, SQLite, notifications
tests/
  TimeTracker.Domain.Tests/
  TimeTracker.Application.Tests/
docs/
  adr/                          # Architecture Decision Records
```

Внутри проектов структура также разделяется по ответственности:

```text
TimeTracker.Application/
  Ports/                         # IClock, INotificationService, repositories
  Timer/                         # TimerCoordinator и use cases таймера
TimeTracker.Domain/
  Timer/                         # TimerSession, TimerPhase, TimerRules
TimeTracker.App/
  Features/Timer/Views/          # XAML-компоненты
  Features/Timer/ViewModels/     # ViewModel компонентов
  Resources/
    Strings.resw                 # базовые/английские ресурсы
    Strings.ru-RU.resw           # русские ресурсы
  Composition/                   # регистрация DI
```

Для самого первого прототипа допустимо начать с одного WinUI-проекта, но публичные доменные правила всё равно следует вынести в отдельные классы и покрыть тестами. Разделение проектов создаётся до появления persistence и внешних интеграций.

## Нефункциональные требования MVP

- Windows 10 1809+ / Windows 11.
- Обычное потребление ресурсов в фоне; приложение не должно постоянно опрашивать систему чаще, чем нужно для отображения секунд.
- Красный overlay всегда поверх обычных окон, но без блокировки клавиатуры и мыши.
- Полоса занимает всю ширину primary monitor и не появляется на дополнительных мониторах.
- Цвета состояния: красный — завершение работы/нужно выбрать действие, зелёный — активный отдых; высота на старте MVP — 64 px.
- Overlay по умолчанию исключается из системного screen capture через `WDA_EXCLUDEFROMCAPTURE`; пользователь может отключить эту опцию.
- Кнопки доступны с клавиатуры, имеют понятный focus state и читаемый контраст.
- Таймер не зависит от точности UI-тикера и не ускоряется/замедляется при задержках отрисовки.
- Логика длительностей покрыта тестами: 25 минут, 5 минут, 90 минут, пятый интервал и Skip.
- Все тексты и длительности в дальнейшем должны быть готовы к локализации и настройкам.
- Критические сценарии таймера имеют автоматические тесты; тесты не ждут реальные минуты и секунды.

## Что не входит в MVP

- учёт приложений и активности клавиатуры/мыши;
- аккаунты, сервер и синхронизация;
- команды, проекты, биллинг и экспорт отчётов;
- сложная аналитика;
- мобильная или macOS-версия;
- принудительная блокировка компьютера.

## План реализации

1. Создать solution и WinUI 3 unpackaged-проект вместе с тестовыми проектами.
2. Написать первые падающие тесты domain-модели и переходов состояний.
3. Реализовать минимальную domain-модель до прохождения тестов.
4. Через TDD добавить `TimerCoordinator` и fake clock.
5. Собрать главное окно и верхний overlay с двумя кнопками, добавляя ViewModel-тесты до UI-кода.
6. Добавить уведомления, автозапуск нового интервала, обработку закрытия окна и исключение overlay из screen capture.
7. Подключить CI-сборку под Windows и обязательный запуск тестов.
8. После проверки UX подключить SQLite для истории и настроек.

## TDD и тестовая стратегия

Тесты разделены по уровням:

- **Domain tests** — чистые быстрые тесты правил и переходов; не используют WinUI, SQLite или реальное время.
- **Application tests** — проверяют use cases, coordinator, порты и взаимодействие с fake adapters.
- **Presentation tests** — проверяют ViewModel, команды, цвета и отображаемое состояние без запуска полноценного UI там, где это возможно.
- **Integration tests** — проверяют SQLite, файловое хранение, Windows-адаптеры и получение primary monitor; запускаются отдельно на Windows.
- **Smoke/E2E tests** — минимальный набор для запуска portable-релиза и базового сценария пользователя.

Каждый тест должен проверять одно наблюдаемое поведение и иметь понятное имя в формате `Method_Scenario_ExpectedResult`. Для времени использовать `FakeClock`/`ManualClock`, а для Windows и persistence — mock/fake реализации портов. Нельзя замедлять тесты через `Task.Delay` на реальные 5 или 25 минут.

Минимальный TDD-процесс для feature:

1. Записать сценарий и критерий готовности.
2. Добавить тест, который сначала падает (`Red`).
3. Написать минимальную реализацию (`Green`).
4. Упростить дизайн, имена и зависимости, сохранив зелёные тесты (`Refactor`).
5. Только после этого подключать UI или инфраструктурный адаптер.

Цель — высокий и осмысленный охват Domain/Application, а не формальный процент покрытия. Непокрытые ветви переходов таймера, локализации и portable-поведения считаются дефектом MVP.

## Локальный запуск после создания проекта

### Работа на macOS

На macOS можно установить .NET 10 SDK и полноценно разрабатывать/тестировать проекты `TimeTracker.Domain`, `TimeTracker.Application` и их тесты. Это основной способ вести TDD для бизнес-логики без Windows.

WinUI 3, Windows App SDK, Win32 API, multi-monitor positioning и portable Windows publish требуют Windows-среду. Их нужно собирать и проверять на Windows 10/11 — физическом ПК, Windows 11 ARM в виртуальной машине на Apple Silicon либо Windows CI runner. Нативно запустить WinUI 3 на macOS нельзя.

Таким образом:

- Mac: Domain/Application, xUnit, fake clock, локализация ресурсов и большая часть TDD;
- Windows/CI: WinUI, XAML, overlay, screen capture exclusion, primary monitor и итоговый ZIP-релиз.

Требования для Windows-разработки: Windows 10/11, Visual Studio 2022/2026 с workload **WinUI application development**, Windows App SDK и .NET 10 SDK.

```powershell
dotnet restore
dotnet build
dotnet test
dotnet run --project src/TimeTracker.App
```

На Mac после установки SDK можно запускать кроссплатформенные тесты отдельно:

```bash
dotnet test tests/TimeTracker.Domain.Tests/TimeTracker.Domain.Tests.csproj
```

Команда запуска `TimeTracker.App` появится после добавления WinUI-проекта и выполняется только на Windows.

Portable-релиз собирается self-contained без MSIX. Пример целевой команды после создания проекта:

```powershell
dotnet publish src/TimeTracker.App -c Release -r win-x64 --self-contained true -p:WindowsAppSDKSelfContained=true -o artifacts/portable/win-x64
```

В релизный каталог добавляются `data/`, README и лицензия; затем каталог архивируется в ZIP. Перед публикацией нужно проверить запуск на чистой Windows-машине без .NET SDK и Windows App SDK runtime.
