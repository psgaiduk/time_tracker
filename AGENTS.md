# Инструкции для AI-агентов и разработчиков

## Контекст проекта

Time Tracker — локальное Windows-приложение с простым таймером работы и отдыха. Основной сценарий: 25 минут работы, затем решение «Пропустить» или «Отдыхать»; отдых обычно 5 минут, после пяти завершённых рабочих интервалов — 90 минут.

## Обязательные архитектурные правила

1. Архитектурный стиль — Hexagonal Architecture / Ports & Adapters.
2. Зависимости направлены внутрь: Presentation → Application → Domain; Infrastructure только реализует порты внутренних слоёв.
3. Бизнес-правила размещаются в `Domain`/`Application`, а не в XAML и code-behind.
4. Domain-проект не имеет ссылок на WinUI, Windows App SDK, SQLite или UI-пакеты.
5. Один публичный тип — один файл; имя файла совпадает с именем типа.
6. View, ViewModel, команда, entity, value object, порт и adapter размещаются в отдельных файлах.
7. Code-behind допускается только для UI-specific операций WinUI; бизнес-логика в нём запрещена.
8. Время измеряется через абстракцию `IClock`; production clock и fake clock для тестов — разные реализации.
9. Источник истины для таймера один — `TimerSession`/coordinator. ViewModel только представляет состояние и вызывает команды.
10. Не считать время по числу UI-тиков. Использовать deadline и фактически прошедшее время.
11. Новые зависимости добавлять только при конкретной пользе для MVP и фиксировать в README или ADR.
12. Не добавлять backend, авторизацию или сбор активности пользователя без отдельного требования.
13. Portable-режим является основным: не добавлять обязательный MSIX, установщик, службу Windows или запись данных в системные каталоги.
14. Путь к данным получать от отдельного `IAppDataPathProvider`; production-реализация по умолчанию использует `data/` рядом с exe.
15. Overlay должен быть отдельным top-level окном, чтобы к нему можно было применить `SetWindowDisplayAffinity` с `WDA_EXCLUDEFROMCAPTURE`.
16. Overlay располагается только на primary monitor, на всю его рабочую ширину; нельзя использовать виртуальную ширину всех мониторов.
17. Локализация обязательна для русского (`ru-RU`) и английского (`en-US`); пользовательские строки нельзя хардкодить в коде.
18. Разработка нового поведения ведётся по TDD: сначала падающий тест, затем минимальная реализация, затем рефакторинг.
19. Учитывать macOS workflow: Domain/Application должны собираться и тестироваться без Windows-зависимостей; WinUI и Windows API изолированы в App/Infrastructure.

## Правила поведения таймера

- Рабочий интервал: 25 минут.
- Короткий перерыв: 5 минут.
- Большой перерыв: 90 минут после пяти завершённых рабочих интервалов.
- `Skip` запускает новый рабочий интервал и не увеличивает/не сбрасывает счётчик.
- Завершение большого перерыва сбрасывает счётчик рабочих интервалов.
- Пятый завершённый рабочий интервал должен вести прямо в большой перерыв, без выбора короткого перерыва.
- Пауза, восстановление после потери фокуса и persistence должны быть отдельными явно описанными решениями, а не неявными побочными эффектами.
- Скрытие overlay из захвата — best-effort-возможность Windows, не механизм защиты от камеры или любого внешнего захвата.

## Рабочий процесс

- Перед изменениями изучить существующие файлы и `git status`.
- Делать небольшие атомарные изменения; не переписывать пользовательские изменения.
- Для нового поведения сначала добавить/обновить тесты доменной логики.
- Не реализовывать новую бизнес-функцию до появления теста, который описывает её ожидаемое поведение.
- После каждого изменения проходить цикл Red → Green → Refactor и сохранять тесты детерминированными.
- После изменений запускать `dotnet test`, затем `dotnet build` на Windows.
- На macOS запускать тесты Domain/Application; Windows-specific проекты проверять на Windows или Windows CI runner.
- Перед коммитом проверить `git diff --check`.
- Для релизных изменений проверять `dotnet publish` в режиме `win-x64`, `--self-contained true`, `WindowsAppSDKSelfContained=true`.
- Portable-артефакт должен запускаться из распакованной папки без предварительной установки .NET, Windows App SDK или прав администратора.
- Не использовать деструктивные команды (`reset --hard`, массовое удаление) без явного запроса.

## Тестовые сценарии, обязательные для таймера

- Start из `Idle` создаёт `Work` на 25 минут.
- Завершение работы с количеством 1–4 создаёт решение о коротком перерыве.
- Завершение работы с количеством 5 создаёт `LongBreak` на 90 минут.
- Skip после решения создаёт новый `Work` на 25 минут.
- Rest создаёт `ShortBreak` на 5 минут.
- После короткого перерыва начинается работа.
- После большого перерыва счётчик сбрасывается.
- Работа при задержке UI-тиков завершается по deadline, а не по числу обновлений.

## TDD и тестовая стратегия

- Domain-тесты не зависят от WinUI, SQLite, Windows API и реальных часов.
- Application-тесты используют fake clock и fake adapters портов.
- Presentation-тесты проверяют команды, состояние ViewModel, цвета и доступность действий.
- Интеграционные тесты отдельно проверяют SQLite, файловые пути, primary monitor и `WDA_EXCLUDEFROMCAPTURE` на Windows.
- Smoke-тест проверяет запуск self-contained portable-артефакта.
- Не использовать реальные `Task.Delay` на минуты; время ускоряется через `FakeClock`/`ManualClock`.
- Имя теста должно описывать поведение: `Method_Scenario_ExpectedResult`.
- Каждая новая ветка бизнес-логики должна иметь тест до реализации.
- Не гнаться за формальным coverage percentage: критичны все переходы таймера, локализация, хранение данных и portable-сценарий.

## Требования к BreakOverlay

- На Windows с одним монитором полоса занимает всю ширину экрана.
- На Windows с несколькими мониторами полоса занимает всю рабочую ширину только primary monitor.
- Временная высота полосы для MVP — 64 px; вынести её в UI-константу, чтобы изменить без переработки архитектуры.
- После окончания рабочей фазы цвет полосы — красный.
- Во время `ShortBreak` и `LongBreak` цвет полосы — зелёный.
- До окончания рабочего времени использовать нейтральный цвет, если дизайн не задаёт отдельный индикатор.
- Не блокировать ввод пользователя на всём экране; интерактивными являются только элементы самой полосы.

## Стиль кода

- Nullable reference types включены.
- Асинхронность — через `async`/`await`; не блокировать UI-поток.
- Публичные интерфейсы и доменные типы имеют ясные имена и XML-комментарии там, где контракт не очевиден.
- Состояния и переходы должны быть перечислимыми и детерминированными.
- Не смешивать форматирование UI (`25:00`) с доменной логикой.
- Пользовательские строки хранить в `.resw` ресурсах; XAML локализовать через `x:Uid`, Application — через абстракцию ресурса.
- Не определять язык через `if`/`switch` в ViewModel. Язык выбирается через отдельный language service и настройки.
- Для каждого нового ключа добавлять значения в русский и английский resource-файлы.
- Не собирать предложения конкатенацией частей, если для языка меняется порядок слов; использовать локализованные форматированные шаблоны.
- Проверять tooltips, accessibility names, ошибки и системные уведомления на обоих языках.
- Не создавать универсальные `Utils`, `Helpers` или `Manager`; каждый класс должен иметь одну понятную ответственность.
- Все зависимости передавать через конструктор; статические глобальные сервисы и service locator запрещены.
- Регистрацию DI держать в одном composition root, например `ServiceRegistration.cs`.
- Типы Windows API, SQLite и WinUI не должны протекать в Domain/Application-контракты.

## Локализация

- Проверять запуск с русским и английским языком Windows.
- Проверять отсутствие обрезания текста на кнопках и в верхней полосе для обоих языков.
- При отсутствии русского ресурса использовать английский fallback и писать диагностическое предупреждение.
- Тесты доменной логики не должны зависеть от языка отображения.
- Mac не является средой проверки WinUI, HWND, multi-monitor и portable Windows publish; для них нужен Windows job.

## Границы MVP

Не реализовывать без отдельного запроса: трекинг приложений, запись нажатий клавиш, удалённый сбор данных, аккаунты, синхронизацию, сложную аналитику и принудительную блокировку устройства.

## Portable-релиз

- Основной формат распространения — ZIP с self-contained unpackaged приложением.
- Данные и логи находятся в `data/` рядом с exe; не полагаться на текущую рабочую директорию процесса.
- Не считать наличие прав записи само собой разумеющимся: при невозможности создать `data/` показать пользователю понятную ошибку с путём.
- Не включать секреты, machine-specific пути и временные файлы в архив.
- После публикации тестировать запуск из пути с пробелами и из папки без прав администратора.

## Screen capture

- Для `BreakOverlay` использовать `SetWindowDisplayAffinity(HWND, WDA_EXCLUDEFROMCAPTURE)` после получения HWND top-level окна.
- Ошибка применения API не должна ломать таймер или закрывать приложение; её нужно диагностировать в логе.
- Не распространять в UI обещание «никто не увидит уведомление»: корректная формулировка — «пытаться скрыть уведомление при демонстрации экрана».
- Проверять Teams, Zoom и Discord отдельно: результат зависит от способа захвата, выбранного конкретным клиентом.
